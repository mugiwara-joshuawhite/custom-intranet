### 3. Trace the outgoing Ethernet and IPv4 headers at s1. Which fields change and which stay unchanged? Why must the IPv4 header checksum be recomputed, and why is that a different job from Ethernet's CRC?
Fields that change at s1: Ethernet source (becomes the MAC the frame was addressed to, i.e. s1's own port MAC), Ethernet destination (becomes the next hop's MAC from the table entry), IPv4 TTL (decreased by 1), and the IPv4 header checksum (recomputed because the TTL changed). Everything else is unchanged: EtherType, IPv4 version, IHL, diffserv, total length, identification, flags, fragment offset, protocol, source IP and destination IP, and the payload. The IP addresses stay the same because they identify the end hosts; only the link-level addresses are rewritten per hop.

The checksum must be recomputed because it covers the IPv4 header, and the TTL is part of that header. Changing the TTL without updating it would leave a wrong checksum, and the next router or host would discard the packet. Ethernet's CRC (the FCS) is a different job: it protects the whole frame on a single link and is generated by the hardware for each frame sent out. The IPv4 checksum protects only the IP header, end to end across hops, and the router (here, the P4 program) must update it explicitly whenever it edits the header.

### 4. Where does the data plane decide what happens when no destination entry matches. In your program, or in the table's default action? Transfer that reasoning to a table with 192.0.2.0/24 forwarding and 192.0.2.64/26 dropping. What happens to 192.0.2.70, and why? This prefix example is written reasoning, not another network experiment.
The decision is made by the table's default action, not by the program's control flow. In MyIngress, `ipv4_lpm` has `default_action = drop();`, so any IPv4 packet that matches no entry is dropped by the table itself. The `apply` block only decides whether to do the lookup (when the IPv4 header is valid); it has no else-branch for misses. (Non-IPv4 frames skip the table entirely, so nothing sets their egress port and they leave on port 0.)

For a table with 192.0.2.0/24 forwarding and 192.0.2.64/26 dropping: 192.0.2.70 is in both prefixes (the /26 covers 192.0.2.64 to 192.0.2.127). Longest-prefix match picks the most specific entry, the /26, so the packet is dropped. The default action is not used because an entry matched. The /24 forward only applies to addresses outside the /26 (e.g. 192.0.2.10), and addresses outside the /24 entirely fall to the default action.
